context boundary / agent data access
Data governance for coding agents

Keep the data out of the context window.

When a coding agent queries Snowflake, the danger isn't the query — it's what comes back. Raw rows that land in the model's context are sent to the model, cached, logged, and shown on screen. The good news: whether that happens is decided at exactly one place, and it's a place you control.

01 — The problem

Helpful agents are indiscriminate about data

A coding agent is built to look at things. Ask it to investigate a table and it will happily SELECT *, read the output, reason over the values, and quote them back to you. That reflex is exactly what makes it useful — and exactly what makes it dangerous against a governed warehouse.

Everything that reaches the context window is, in effect, published:

  • It is sent to the model provider as part of the prompt on every subsequent turn.
  • It is persisted — in the session transcript, in prompt caches, in any logging or observability layer you've wired up.
  • It is rendered to the user, who may not be entitled to see those specific rows.

For PII, PHI, card data, or anything under a data-residency or least-privilege regime, a single SELECT customer_email, ssn FROM … that prints its results is an exfiltration event — not because anyone was malicious, but because the agent did its job well. Prompting it to “be careful with sensitive data” is not a control; it's a suggestion the model will honor most of the time and drop under pressure in a long or ambiguous session.

02 — The key insight

The tool boundary decides exposure — not the agent

The agent is never connected to Snowflake. It emits a request and gets a result. In between sits the executing tool — the MCP server or the script — which holds the credentials and receives the rows. Whether those rows continue on into the context window is a property of what that tool chooses to return.

Context leakage is set by the tool's return contract, not by the model's intent. Control the return surface and you control exposure.

// the thesis behind flake-fetch-flow — the tool holds a reference, like a pointer in C

This reframes the whole problem. You are not trying to make a capable, curious agent behave. You are designing a boundary so that the sensitive data has no path into context in the first place. A tool that writes results to a Parquet file and returns { path, rows, schema } cannot leak a single value — there is nothing to leak, by construction. The agent can then load, aggregate, and analyze that file with tools that likewise return only shapes and summaries.

Once you see the boundary clearly, the guardrails sort themselves into a ladder — from advisory at the top to structural at the bottom.

03 — Recommendations

Defense in depth, ordered by how hard it is to bypass

The goal is to push enforcement as far down this ladder as you can. Higher layers are easy to add and easy to defeat; lower layers make leakage structurally impossible or neutralize the data at its source.

L0

Prompt & CLAUDE.md instructions weakest · advisory

“Never print raw rows; always write to a file.” Useful as intent-setting and documentation, but it relies on model compliance. Necessary, never sufficient.

L1

Hooks & permissions deterministic · reactive

A PreToolUse hook or a permission deny-list blocks any call that would stream rows into context. Deterministic and uncircumventable by the model — but it pattern-matches the symptom. See §04.

L2

Tool return contract structural · leak-proof

The tool cannot return rows — it writes to disk or a stage and returns only a reference and metadata. This is the real fix: when there is nothing to block, the L1 hook has nothing to do.

L3

Data-layer governance strongest · at the source

Least-privilege roles, row-access policies, and dynamic data masking in the warehouse. Even a value that is returned comes back masked. Enforced by the database, independent of any agent.

Return-a-reference, not a resultset

The L2 layer is just a discipline about what the tool hands back. These are the patterns cataloged in flake-fetch-flow, sorted by whether data crosses the boundary:

PatternWhat the tool returnsBoundary
Rows via MCP up to N result rows ◆ enters context
Script → stdout printed table / console text ◆ enters context
MCP → CSV/Parquet { path, row_count } ◆ stays local
Script → file stream one metadata line ◆ stays local
DataFrame load { shape, dtypes } ◆ stays local
Metadata-only schema / counts / aggregates by design ◆ stays local

Same warehouse, same SQL, same agent. The only variable is the tool's return value — which is why the boundary, not the model, is where you invest.

04 — Hooks & permissions as a guardrail

The deterministic net you build to later throw away

Instructions ask; hooks enforce. A PreToolUse hook receives the pending tool call as JSON on stdin, inspects it, and — by exiting with status 2 — blocks the call and feeds its stderr back to the model as the reason. Because the harness runs it, not the model, it holds even in a long or adversarial session. That makes hooks the right tool while your data tools are still capable of leaking.

Permissions give you the coarse cut: deny the row-returning paths outright, allow only the sanctioned file-writing script.

.claude/settings.json
// Close the direct-to-stdout paths; leave one sanctioned door open.
{
  "permissions": {
    "deny": [
      "Bash(snow sql:*)",           // Snowflake CLI prints rows
      "Bash(snowsql:*)",
      "mcp__snowflake__run_query"     // row-returning MCP tool
    ],
    "allow": [
      "Bash(python scripts/query_to_parquet.py:*)"
    ]
  },
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [ { "type": "command",
          "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/block-raw-data.sh" } ] }
    ]
  }
}

A hook catches what a static deny-list can't — the SQL smuggled through an allowed interpreter, a new CLI flag, a pipe to cat. It reads the actual command and refuses anything that would put rows on stdout:

.claude/hooks/block-raw-data.sh
#!/usr/bin/env bash
# PreToolUse: refuse commands that would stream query rows into context.
set -euo pipefail

payload="$(cat)"
cmd="$(printf '%s' "$payload" | jq -r '.tool_input.command // ""')"

# Any direct Snowflake client that renders a resultset to the terminal.
if printf '%s' "$cmd" | grep -Eiq '(snow[[:space:]]+sql|snowsql|\.fetchall\(|SELECT .* --format)'; then
  echo "Blocked: this would print rows into the model context." >&2
  echo "Use scripts/query_to_parquet.py — it returns only {path, rows, schema}." >&2
  exit 2   # exit 2 = block the call, return stderr to the model
fi

exit 0
◆ Why we want to eliminate this layer

A hook is a net under a leaky pipe. It is deterministic, which is genuinely better than a prompt — but it is reactive: it enumerates the ways a capable tool could spill data and races the agent to block each one. Every new client, flag, or interpreter is a fresh gap, and the regex that guards you is only as good as the last leak you imagined.

The tell that you've fixed the real problem is that the hook stops firing — because the tools it guards can no longer return rows at all (L2), and anything that slips through comes back masked at the source (L3). Ship the hook today so you're covered while the tools are still leaky; treat the day you can delete it as the milestone. The strongest guardrail is the one you no longer need.

Note: project settings live in the repo and can be edited by anyone who can edit the repo. For a boundary that users and agents cannot relax, deploy the same rules as managed settings — admin-controlled and not overridable locally — which is the only way to enforce a deterministic, organization-wide guardrail.

05 — Where to land

Make leakage impossible, then make the block unnecessary

Aim the design so that the answer to “could this expose a raw value?” is no, by construction — not no, because something blocked it in time. That means tools whose return contract is a reference plus metadata, warehouse governance that masks at the source, and hooks and permissions kept on as a deterministic safety net you are actively trying to render redundant.

  • Design the tool boundary first. Return { path, rows, schema }, never resultsets. This is the layer that actually removes the risk.
  • Govern at the source. Row-access policies and dynamic masking in Snowflake protect you even when a value does come back.
  • Keep hooks & permissions as the net. Deterministic coverage for the gap between today's leaky tools and tomorrow's leak-proof ones — and prefer managed settings when the boundary must hold org-wide.
  • Use prompts for intent, not enforcement. Document the contract in CLAUDE.md; never rely on it to hold the line.
